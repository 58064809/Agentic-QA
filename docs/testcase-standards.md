# 测试用例标准

`testcases` 的事实形态是强类型 `TestCaseSet`。模型只生成结构化规则、用例和覆盖映射；Harness
先执行确定性校验，再把通过校验的数据渲染成 Markdown Candidate；模型输出停留在
结构化对象，不参与 Markdown 大表格拼接。

## 固定 11 列

| # | 列名 | 系统读取的内容 | 校验会报告的情况 |
|---:|---|---|---|
| 1 | 用例ID | 唯一、稳定的 `TC-*` 标识 | 重复或空 ID |
| 2 | 需求/规则来源 | `RequirementCatalog` 中存在的规则 ID | 泛化来源或不存在的规则 |
| 3 | 标题 | 单一可验证目标 | 把多个独立规则塞进一条用例 |
| 4 | 测试类型 | 功能、边界、异常、状态迁移、权限等 | 空泛“其他” |
| 5 | 优先级 | 与 `RiskCatalog` 一致的 P0–P3 | 无依据夸大风险 |
| 6 | 前置条件 | 可建立的状态、账号、权限、环境 | 假设不存在的能力 |
| 7 | 测试数据 | 具体值或可重复的生成约束 | 真实敏感数据 |
| 8 | 测试步骤 | 有序、可执行的操作 | “执行测试”等无法落地的描述 |
| 9 | 预期结果 | 来源支持的可观察业务结果 | 把推测写成事实 |
| 10 | 断言/证据 | 可观察状态、输出、截图或记录 | 仅“成功”“正常”“符合预期” |
| 11 | 待确认项 | 缺失规则、数据、环境或观察点 | 用占位词掩盖关键缺口 |

每条 Markdown 用例保持一个物理行，多步骤由确定性渲染器转换为 `<br>`，单元格中的竖线会转义。

## 强类型完整性门

新写入使用 `TestCaseSet v2`。生成前先验证 `TestDesignPlan`，并绑定 RequirementCatalog、RiskCatalog v2
和 plan 的内容 Hash；v1 仅用于历史导入。设计方法按证据启用：boundary/state 需要结构化声明，decision
table 需要至少两个条件和多个结果，pairwise 需要至少三个多值独立因子，cause-effect 需要可引用关系，
role × state × config 需要三维均有证据。error guessing 仅来自历史缺陷，regression 仅来自 Delta、Impact
或历史覆盖，negative testing 用于约束、异常、权限与无效输入。

组合预算为最多 8 因子、每因子 12 值、100 组合；超限形成 pending item，不静默丢失。新用例内部
规范化 Hash 重复直接拒绝；历史相似度达到 0.90 只产生 `covered | regression_gap |
intentionally_distinct` 复核决策，不自动复制或删除。

生成阶段在渲染前验证：

- 规则 ID、用例 ID 和覆盖映射均唯一；
- 覆盖矩阵引用不存在的用例，或用例缺少对应规则声明；
- 每条 confirmed 规则均有覆盖映射；
- 声明的边界值存在未覆盖项目；
- 声明的状态迁移存在未覆盖项目；
- 用例步骤可执行，预期和断言可观察；
- 不接受重复用例、空泛断言或未知规则；
- 输出出现 `forbidden_inventions` 中且来源没有定义的页面、接口、字段或数据库细节。

渲染后，`generic-artifact-contracts` 会重新解析 Markdown，复验 11 列、用例引用、覆盖矩阵、占位
映射、原子性和来源未支持的实现细节。此门负责确定性审核，人工 Review Gate 仍负责批准决定。

## 覆盖矩阵

| 要求 | 验证 |
|---|---|
| 一条规则一个映射项 | 重复规则映射返回校验错误 |
| 映射用例真实存在 | 不接受悬空 ID |
| 用例声明对应规则 | 不接受矩阵与主表相互矛盾 |
| confirmed 规则全部覆盖 | 缺失即 blocker |
| 边界和状态迁移完整 | 按 RequirementCatalog 逐项核对 |
| 映射依据具体 | 不接受“暂无”“待补充”“后续设计” |

## 证据真实性

仅完整 OpenAPI 可确认 API endpoint；仅来源明确的页面、角色、字段和配置可写成确定事实。来源
证据不足时，缺口会出现在待确认项中；来源没有定义的实现细节会被质量门报告。Candidate 尚未
执行时，其状态保持设计候选，不会呈现为 passed 或实际结果。
